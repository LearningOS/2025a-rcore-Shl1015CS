# Lab5 实验报告

## 功能实现总结

本次实验实现了基于简化银行家算法的死锁检测机制。主要功能包括：

1. **死锁检测数据结构**：在`ProcessControlBlockInner`中添加了`available_mutex`和`available_semaphore`计数器，用于跟踪各类资源的可用数量，以及`en_deadlock_detect`标志控制检测开关。

2. **系统调用实现**：实现了`sys_enable_deadlock_detect`系统调用（ID: 469），允许进程动态开启或关闭死锁检测功能。

3. **死锁检测逻辑**：在`sys_mutex_lock`和`sys_semaphore_down`中集成检测算法。当资源不可用且可能导致死锁时，拒绝资源请求并返回`-0xDEAD`。对于信号量，还会检查就绪任务数量以避免进程内死锁。

4. **代码优化**：通过添加辅助函数、完善错误处理、边界检查和性能优化，提升了代码的健壮性和可维护性。

该实现采用简化策略，对互斥锁和信号量分别进行检测，在保证功能正确性的同时降低了复杂度。

## 问答作业

### 1. 主线程退出时的资源回收

当主线程（0号线程）退出时，需要回收的资源包括：

**需要回收的资源：**
- **内存资源**：进程的地址空间（`MemorySet`）、用户栈、内核栈
- **文件资源**：文件描述符表中打开的文件句柄
- **同步原语**：进程内的互斥锁、信号量、条件变量
- **线程资源**：所有子线程的`TaskControlBlock`、线程私有栈空间
- **进程标识符**：PID资源需要释放供后续进程使用
- **父子关系**：从父进程的children列表中移除，处理孤儿进程

**TaskControlBlock的引用位置及回收策略：**

1. **任务管理器的就绪队列**：需要回收。这些线程已无法继续执行，应从调度器中移除。

2. **进程的tasks向量**：需要回收。这是进程管理线程的主要数据结构。

3. **等待队列**（如互斥锁、信号量的wait_queue）：需要回收。等待的线程应被唤醒并设置错误状态。

4. **定时器队列**：需要回收。正在sleep的线程应被移除。

5. **父进程的引用**：不需要特殊处理。父进程通过弱引用管理子进程，子进程退出时自然解除。

### 2. 两种Mutex实现的区别

**主要区别：**

**Mutex1（有循环）**：
```rust
fn lock(&self) {
    loop {  // 关键差异：使用循环
        if mutex_inner.locked {
            // 加入等待队列并阻塞
        } else {
            mutex_inner.locked = true;
            break;
        }
    }
}
```

**Mutex2（无循环）**：
```rust
fn lock(&self) {
    // 只检查一次
    if mutex_inner.locked {
        // 加入等待队列并阻塞
    } else {
        mutex_inner.locked = true;
    }
}
```

**可能导致的问题：**

1. **竞态条件**：Mutex2存在严重的竞态条件问题。当线程从`block_current_and_run_next()`被唤醒后，不会重新检查锁状态，可能在锁仍被占用时错误地认为获得了锁。

2. **锁状态不一致**：Mutex2中，线程被唤醒后直接返回，但此时`mutex_inner.locked`可能仍为`true`（因为unlock中只有在没有等待线程时才设置为false）。

3. **内存安全问题**：多个线程可能同时认为自己获得了锁，导致临界区保护失效。

4. **活锁风险**：在高并发场景下，Mutex1的循环可能导致线程反复尝试获锁，增加CPU开销。

**正确的实现应该**：
- 线程被唤醒后重新检查锁状态（如Mutex1）
- 或者在unlock时直接将锁传递给等待线程，确保状态一致性
